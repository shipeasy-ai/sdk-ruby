# i18n (Rails view helpers)

**This SDK has i18n.** Although it's a server SDK, the gem ships server-side i18n
view helpers for Rails (translated label rendering at SSR) plus loader tags for
the browser SDK. The same `Shipeasy.configure` covers it — there is no separate
i18n init.

## Configure

i18n uses the **public client key** (not the server key) and a `profile`:

```ruby
Shipeasy.configure do |c|
  c.api_key    = ENV.fetch("SHIPEASY_SERVER_KEY")
  c.public_key = ENV.fetch("SHIPEASY_CLIENT_KEY")   # for i18n
  c.profile    = "{{PROFILE}}"
end
```

## Rails view helpers

When Rails is loaded, the Railtie auto-mounts these helpers — no include needed:

```erb
<%# Renders <script id="i18n-data" ...> inline data + the loader <script> tag: %>
<%= i18n_head_tags %>

<h1><%= i18n_t("hero.title", name: current_user.name) %></h1>
```

| Helper | Purpose |
| --- | --- |
| `i18n_head_tags(profile:)` | Inline label JSON + loader `<script>` tag for `<head>`. |
| `i18n_inline_data(profile:)` | Just the inline `application/json` label blob. |
| `i18n_script_tag(hide_until_ready:)` | Just the loader `<script>` (uses `config.public_key` + `config.profile`). |
| `i18n_t(key, variables = {}, profile:)` | Render a translated label server-side, interpolating `{{var}}` placeholders. Falls back to the key if missing. |

`i18n_t` resolves the label from the fetched label file for the configured
profile and interpolates `{{name}}`-style variables. If the key is absent it
returns the key verbatim. Publishing is profile-wide — a profile is snapshotted
and served as one blob, so the profile is the only thing you select.

## Render keys only (testing)

For tests and snapshots, resolving copy is a liability: an assertion on
`"Place order"` breaks the moment someone edits that translation. Set
`render_keys_only` and `i18n_t` returns the **key itself** —
`i18n_t("checkout.cta")` yields `"checkout.cta"` — so you assert against the
stable key, not the copy (no fetch, no interpolation).

It **defaults on when the native env is `"test"`** (`RAILS_ENV` / `RACK_ENV` /
`SHIPEASY_ENV` / `APP_ENV`), so most RSpec/Rails suites need no configuration.
Set it explicitly to override the env default in either direction:

```ruby
Shipeasy.configure do |c|
  c.api_key          = ENV.fetch("SHIPEASY_SERVER_KEY")
  c.render_keys_only = true   # force on (e.g. request/system specs)
end
```

## SSR i18n loader tag (framework-agnostic)

The package-level helper emits the loader tag anywhere — Rails, Sinatra, a plain
ERB template. **Every argument is optional**: it reads what `Shipeasy.configure`
already set, so the normal call carries no arguments at all. The tag carries the
**public client key**, never the server key:

```erb
<%= Shipeasy.i18n_script_tag %>
```

Under Rails the returned tag is `html_safe`, so no `.html_safe` at the callsite.
Pass an argument only to override the configured value for that one tag:

```ruby
# i18n_script_tag(client_key = nil, profile: nil, base_url: nil)
#   client_key — PUBLIC client key   (default: config.public_key)
#   profile    — locale profile      (default: config.profile)
#   base_url   — CDN base            (default: config.cdn_base_url)
Shipeasy.i18n_script_tag("sdk_client_…", profile: "{{PROFILE}}")
```

`Shipeasy.bootstrap_script_tag` takes the same `i18n_profile:` default, so the
browser hydrates the same profile without being told twice (see
[advanced](advanced.md)).

## Cross-SDK story

The browser SDK loads translations via the loader `<script>` (data-key = the
public client key, data-profile = the profile) and exposes `t()` client-side.
The Ruby helpers render the same `{{PROFILE}}` profile server-side so the first
paint is already translated.
